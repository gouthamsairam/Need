# React.js Interview Questions & Answers

## Basic → Intermediate → Senior Developer

# 1. React Fundamentals

### 1. What is React.js?

**Answer:**

React.js is a JavaScript library developed by Meta for building user interfaces, especially single-page applications.

React allows us to build applications using reusable components.

The main concepts are:

* Components
* JSX
* Props
* State
* Hooks
* Virtual DOM
* Reconciliation
* Context
* Routing
* State management

### Follow-up: Is React a framework or a library?

**Answer:**

React is primarily a **UI library**, not a complete framework.

React mainly handles the UI layer. For routing, API communication, state management, etc., we commonly use additional libraries.

For example:

```text
React
   ↓
UI

React Router
   ↓
Routing

Redux / Zustand
   ↓
Global State

Axios / Fetch
   ↓
API communication
```

---

### 2. Why do we use React?

**Answer:**

React provides:

1. Reusable components
2. Efficient UI updates
3. Declarative programming
4. Component-based architecture
5. Strong ecosystem
6. Hooks for state and lifecycle behavior
7. Good developer tooling
8. Support for large-scale applications

### Follow-up: What is the biggest advantage of React?

**Answer:**

One major advantage is **component reusability**.

For example, instead of creating separate HTML code for every button:

```jsx
<Button />
```

we can create one reusable component and use it throughout the application.

# 2. JSX

### 3. What is JSX?

**Answer:**

JSX stands for **JavaScript XML**.

It allows us to write HTML-like syntax inside JavaScript.

Example:

```jsx
const element = <h1>Hello World</h1>;
```

JSX is transformed into JavaScript before it runs in the browser.

Conceptually:

```jsx
<h1>Hello World</h1>
```

becomes something similar to:

```javascript
React.createElement("h1", null, "Hello World");
```

Modern React uses the automatic JSX transform, so explicit `React.createElement` calls are generally generated by the build tooling rather than written manually.

### Follow-up: Can the browser directly understand JSX?

**Answer:**

No.

JSX needs to be transformed into regular JavaScript by tools such as Babel or the framework's build tooling.

---

### 4. What are the rules of JSX?

**Answer:**

Important rules include:

1. Return a single root element, or use a Fragment.
2. Close all tags.
3. Use `className` instead of `class`.
4. Use camelCase for most DOM properties.
5. JavaScript expressions are written inside `{}`.

Example:

```jsx
function User() {
    const name = "John";

    return (
        <div className="user">
            <h1>{name}</h1>
        </div>
    );
}
```

### Follow-up: Why do we use `className` instead of `class`?

**Answer:**

Because `class` is a JavaScript reserved keyword. React uses `className` to represent the DOM `class` attribute.

---

# 3. Virtual DOM

### 5. What is Virtual DOM?

**Answer:**

The Virtual DOM is an in-memory representation of the UI.

When state or props change, React creates/reconciles the new element tree and determines what needs to change in the actual DOM.

Conceptually:

```text
State changes
     ↓
React creates new element tree
     ↓
Reconciliation
     ↓
Determine required DOM changes
     ↓
Browser DOM updated
```

### Follow-up: Is Virtual DOM always faster than the DOM?

**Answer:**

Not necessarily.

The Virtual DOM is an abstraction that helps React efficiently manage UI updates. Performance depends on the application, rendering patterns, DOM complexity, and how the code is written.

---

# 4. Reconciliation

### 6. What is reconciliation?

**Answer:**

Reconciliation is the process React uses to determine how the UI should change when the component tree changes.

React compares the previous and next rendered element trees and determines which updates are required.

### Follow-up: What role do keys play in reconciliation?

**Answer:**

Keys help React identify list items across renders.

Example:

```jsx
users.map(user => (
    <User key={user.id} user={user} />
))
```

React can then determine which item:

* Was added
* Was removed
* Was moved
* Was updated

# 5. Components

### 7. What is a component?

**Answer:**

A component is a reusable piece of UI and its associated behavior.

Example:

```jsx
function Welcome() {
    return <h1>Welcome</h1>;
}
```

We can use it as:

```jsx
<Welcome />
```

### Follow-up: What are the types of React components?

Historically:

* Functional components
* Class components

Modern React primarily uses **function components with Hooks**.

# 6. Props

### 8. What are props?

**Answer:**

Props are inputs passed from a parent component to a child component.

Example:

```jsx
function User({ name }) {
    return <h1>{name}</h1>;
}

function App() {
    return <User name="John" />;
}
```

Here:

```text
App
 ↓
name="John"
 ↓
User
```

### Follow-up: Can a child modify props?

**Answer:**

No.

Props should be treated as **read-only**.

If the child needs to request a change, the parent can pass a callback.

```jsx
function Parent() {

    const handleUpdate = () => {
        console.log("Updated");
    };

    return <Child onUpdate={handleUpdate} />;
}
```

---

# 7. State

### 9. What is state?

**Answer:**

State represents data that can change during the lifetime of a component and affect what it renders.

Example:

```jsx
const [count, setCount] = useState(0);
```

When we call:

```jsx
setCount(1);
```

React schedules an update and the component can render with the new state.

### Follow-up: What is the difference between props and state?

| Props                  | State                                 |
| ---------------------- | ------------------------------------- |
| Passed by parent       | Managed by component                  |
| Read-only              | Updated through state setter/dispatch |
| Used for communication | Used for changing UI/data             |
| External input         | Internal component data               |

---

# 8. useState

### 10. What is `useState()`?

**Answer:**

`useState` is a React Hook that allows function components to store state.

```jsx
const [count, setCount] = useState(0);
```

Here:

```text
count     → current state
setCount  → state update function
0         → initial value
```

### Follow-up: Why should we use the functional form of state update?

Suppose the new state depends on the previous state:

```jsx
setCount(prev => prev + 1);
```

This is preferred over:

```jsx
setCount(count + 1);
```

when multiple updates depend on the previous state.

Example:

```jsx
setCount(prev => prev + 1);
setCount(prev => prev + 1);
```

This correctly represents two increments.

---

# 9. State Immutability

### 11. Why should we not directly modify state?

Incorrect:

```jsx
user.name = "John";
```

Instead:

```jsx
setUser({
    ...user,
    name: "John"
});
```

React relies heavily on detecting changes through references and rendering semantics. Mutating existing state objects directly can lead to incorrect UI behavior and makes state updates harder to reason about.

### Follow-up: How do you update an array in state?

Instead of:

```jsx
users.push(user);
```

use:

```jsx
setUsers(prev => [...prev, user]);
```

Remove:

```jsx
setUsers(prev =>
    prev.filter(user => user.id !== id)
);
```

Update:

```jsx
setUsers(prev =>
    prev.map(user =>
        user.id === id
            ? { ...user, name: "John" }
            : user
    )
);
```

# 10. Event Handling

### 12. How does event handling work in React?

Example:

```jsx
function App() {

    const handleClick = () => {
        console.log("Clicked");
    };

    return (
        <button onClick={handleClick}>
            Click
        </button>
    );
}
```

We pass a function rather than immediately calling it.

Correct:

```jsx
onClick={handleClick}
```

Incorrect:

```jsx
onClick={handleClick()}
```

### Follow-up: How do you pass parameters?

```jsx
<button onClick={() => handleClick(id)}>
    Delete
</button>
```

# 11. Conditional Rendering

### 13. How do you conditionally render components?

Using ternary:

```jsx
{
    isLoggedIn
        ? <Dashboard />
        : <Login />
}
```

Using `&&`:

```jsx
{
    isAdmin && <AdminPanel />
}
```

### Follow-up: What is the problem with `count && <Component />`?

If:

```jsx
count = 0;
```

then:

```jsx
0 && <Component />
```

results in `0`, which React can render.

A safer approach is:

```jsx
count > 0 && <Component />
```

# 12. Lists and Keys

### 14. Why are keys required?

Example:

```jsx
users.map(user => (
    <User
        key={user.id}
        user={user}
    />
))
```

Keys provide stable identity for list elements.

### Follow-up: Can we use array index as key?

Technically yes, but it can be problematic when the list can be reordered, inserted into, or deleted from.

Prefer:

```jsx
key={user.id}
```

over:

```jsx
key={index}
```

when a stable unique ID is available.

# 13. useEffect

### 15. What is `useEffect()`?

**Answer:**

`useEffect` allows a component to synchronize with external systems or perform side effects.

Examples include:

* API requests
* Browser APIs
* subscriptions
* timers
* event listeners

Example:

```jsx
useEffect(() => {
    console.log("Component rendered");
}, []);
```

### Follow-up: What does the dependency array do?

```jsx
useEffect(() => {
    console.log("Effect");
}, [userId]);
```

The effect is re-run when the dependency values change.

### Follow-up: What does an empty dependency array mean?

```jsx
useEffect(() => {
    loadData();
}, []);
```

It means the effect doesn't react to changes in dependencies because there are none specified. In typical client-side usage, it runs after the initial mount.

# 14. useEffect Cleanup

### 16. Why do we need cleanup?

For resources such as:

* Event listeners
* Timers
* Subscriptions
* WebSocket connections

Example:

```jsx
useEffect(() => {

    const handler = () => {
        console.log(window.scrollY);
    };

    window.addEventListener("scroll", handler);

    return () => {
        window.removeEventListener("scroll", handler);
    };

}, []);
```

### Follow-up: What happens if we don't clean up?

You can get:

* Memory/resource leaks
* Duplicate subscriptions
* Unexpected callbacks
* Performance problems

# 15. useEffect vs useLayoutEffect

### 17. Difference between `useEffect` and `useLayoutEffect`?

`useEffect` generally runs after the browser has had an opportunity to paint.

`useLayoutEffect` runs synchronously after DOM mutations but before the browser paints.

Use `useLayoutEffect` when you need to measure or synchronously adjust layout before the user sees it.

Example:

```jsx
useLayoutEffect(() => {
    // measure DOM
});
```

### Follow-up: Should we use `useLayoutEffect` everywhere?

**No.**

Prefer `useEffect` unless you specifically need layout synchronization.

---

# 16. useRef

### 18. What is `useRef()`?

`useRef` provides a mutable value that persists between renders without causing a re-render when changed.

Example:

```jsx
const inputRef = useRef();

<input ref={inputRef} />
```

Then:

```jsx
inputRef.current.focus();
```

### Follow-up: Does changing `ref.current` cause re-render?

No.

```jsx
countRef.current++;
```

does not itself cause a render.

---

# 17. useMemo

### 19. What is `useMemo()`?

`useMemo` caches the result of a calculation between renders until its dependencies change.

```jsx
const result = useMemo(() => {
    return expensiveCalculation(data);
}, [data]);
```

### Follow-up: Should we use useMemo everywhere?

No.

It has its own overhead. Use it when memoization provides a meaningful performance benefit.

---

# 18. useCallback

### 20. What is `useCallback()`?

`useCallback` memoizes a function reference.

```jsx
const handleClick = useCallback(() => {
    console.log("Clicked");
}, []);
```

This can be useful when passing callbacks to memoized children or when a stable function identity matters.

### Follow-up: Difference between useMemo and useCallback?

```jsx
useMemo
```

memoizes a **value**.

```jsx
useCallback
```

memoizes a **function reference**.

Conceptually:

```jsx
useMemo(() => calculate(), [data]);

useCallback(() => handleClick(), [data]);
```

---

# 19. React.memo

### 21. What is `React.memo()`?

`React.memo` lets React skip re-rendering a component when its props are considered unchanged.

Example:

```jsx
const User = React.memo(function User({ name }) {
    return <h1>{name}</h1>;
});
```

### Follow-up: Does React.memo prevent all re-renders?

No.

The component can still render when:

* Its own state changes
* A context it consumes changes
* Its parent passes changed props

# 20. Context API

### 22. What is Context API?

Context provides a way to share values with components deeper in the tree without passing props through every intermediate component.

Example:

```jsx
const UserContext = createContext(null);
```

Provider:

```jsx
<UserContext.Provider value={user}>
    <Dashboard />
</UserContext.Provider>
```

Consumer:

```jsx
const user = useContext(UserContext);
```

### Follow-up: Is Context a replacement for Redux?

Not necessarily.

Context is useful for things like:

* Theme
* Locale
* Authentication information
* Dependency/configuration-like values

A dedicated state-management library may be more appropriate for complex, frequently changing application state.

# 21. Prop Drilling

### 23. What is prop drilling?

Prop drilling occurs when data is passed through multiple intermediate components that don't actually need the data.

```text
App
 ↓
A
 ↓
B
 ↓
C
 ↓
User
```

If only `User` needs the data, passing it through A, B and C can become cumbersome.

### Follow-up: How can we solve prop drilling?

Possible approaches:

1. Component composition
2. Context
3. State-management libraries
4. Restructuring component boundaries

# 22. Controlled Components

### 24. What is a controlled component?

A controlled input gets its value from React state.

```jsx
const [name, setName] = useState("");

<input
    value={name}
    onChange={e => setName(e.target.value)}
/>
```

React is the source of truth.

### Follow-up: What is an uncontrolled component?

The DOM maintains the input's current value.

```jsx
const inputRef = useRef();

<input ref={inputRef} />
```

You can then access:

```jsx
inputRef.current.value
```

# 23. Hooks

### 25. What are Hooks?

Hooks allow function components to use React features such as state, context, refs, and effects.

Common hooks:

```text
useState
useEffect
useContext
useRef
useMemo
useCallback
useReducer
useLayoutEffect
```

Modern React also includes newer APIs such as:

```text
useTransition
useDeferredValue
useId
useSyncExternalStore
useImperativeHandle
```

### Follow-up: What are the Rules of Hooks?

Hooks should:

1. Be called at the top level.
2. Not be called inside loops.
3. Not be called inside conditions.
4. Not be called inside nested functions.
5. Be called from React components or custom Hooks.

Incorrect:

```jsx
if (isLoggedIn) {
    useEffect(...);
}
```

Correct:

```jsx
useEffect(() => {
    if (isLoggedIn) {
        // logic
    }
}, [isLoggedIn]);
```

# 24. Custom Hooks

### 26. What is a custom Hook?

A custom Hook is a reusable function that uses React Hooks to encapsulate reusable behavior.

Example:

```jsx
function useFetch(url) {

    const [data, setData] = useState(null);

    useEffect(() => {
        fetch(url)
            .then(res => res.json())
            .then(setData);
    }, [url]);

    return data;
}
```

Usage:

```jsx
const users = useFetch("/api/users");
```

### Follow-up: Why do we create custom Hooks?

To reuse **logic**, not UI.

For example:

```text
useAuth()
useFetch()
useDebounce()
useLocalStorage()
useWindowSize()
```

# 25. useReducer

### 27. What is `useReducer()`?

`useReducer` is useful for managing state transitions using actions and a reducer function.

Example:

```jsx
const [state, dispatch] = useReducer(reducer, initialState);
```

Reducer:

```jsx
function reducer(state, action) {

    switch (action.type) {

        case "increment":
            return {
                ...state,
                count: state.count + 1
            };

        default:
            return state;
    }
}
```

Dispatch:

```jsx
dispatch({ type: "increment" });
```

### Follow-up: useState vs useReducer?

Use `useState` for simpler state.

Use `useReducer` when:

* State has multiple related fields
* Many actions can change the state
* State transitions are complex
* You want centralized state-transition logic

# 27. Redux Toolkit

### 29. Why is Redux Toolkit preferred?

Redux Toolkit is the recommended way to write Redux logic because it simplifies:

* Store configuration
* Reducers
* Actions
* Immutable updates
* Async logic
* Boilerplate

Example:

```jsx
const counterSlice = createSlice({
    name: "counter",

    initialState: {
        count: 0
    },

    reducers: {
        increment(state) {
            state.count++;
        }
    }
});
```

### Follow-up: Isn't `state.count++` mutation?

It looks like mutation, but Redux Toolkit uses **Immer**, which tracks these changes and produces the appropriate immutable update.

# 28. React Router

### 30. What is React Router?

React Router is commonly used to provide client-side routing in React applications.

Example:

```jsx

    <Route path="/users" element={<Users />} />
    <Route path="/products" element={<Products />} />
```

Client-side routing can change the displayed UI without requiring a full page reload for every navigation.

Server-side routing typically involves the browser requesting a new document from the server.

# 29. Lazy Loading

### 31. What is lazy loading in React?

Lazy loading allows code to be loaded when it is needed instead of loading everything initially.

```jsx
const Admin = lazy(() => import("./Admin"));
```

Then:

```jsx
<Suspense fallback={<Loading />}>
```

### Follow-up: Why use lazy loading?

It can reduce the initial JavaScript payload and improve initial loading performance.

# 30. Suspense

### 32. What is Suspense?

`Suspense` allows React to display fallback UI while a child is not yet ready.

Example:

```jsx
<Suspense fallback={<Loading />}>
    <Admin />
</Suspense>
```

A common use case is lazy-loaded components.

Modern React also uses Suspense in broader rendering/data-loading architectures.

# 31. Error Boundaries

### 33. What is an Error Boundary?

An Error Boundary is a component that catches certain rendering errors in its descendant tree and displays fallback UI instead of allowing the entire UI subtree to crash.

Historically, Error Boundaries are implemented using class lifecycle methods such as:

```jsx
static getDerivedStateFromError()
```

and:

```jsx
componentDidCatch()
```

### Follow-up: Can try-catch replace Error Boundaries?

No.

A `try-catch` around event-handler or arbitrary JavaScript code is different from React's render error handling.

Error Boundaries are specifically designed for errors occurring during React rendering/lifecycle processing of a descendant tree.

# 32. Component Lifecycle

### 34. Explain the React component lifecycle.

For class components, the traditional lifecycle is:

```text
Mounting
   ↓
Updating
   ↓
Unmounting
```

Examples:

```text
componentDidMount
componentDidUpdate
componentWillUnmount
```

With function components, Hooks such as `useEffect` are used for synchronization and cleanup rather than directly reproducing the old lifecycle model.

# 33. Rendering

### 35. What causes a React component to render?

Common causes include:

* Initial rendering
* State updates
* Parent rendering
* Context changes
* External store updates

### Follow-up: Does a state update always immediately update the DOM?

No.

React schedules rendering work. Updates can be **batched**, and React determines when and how to commit the necessary DOM changes.

# 34. Batching

### 36. What is automatic batching?

React can group multiple state updates into fewer renders.

Example:

```jsx
setCount(c => c + 1);
setName("John");
```

React can batch these updates so they don't necessarily cause separate renders.

This behavior was expanded in React 18 to cover more asynchronous contexts.

`StrictMode` is a development-only tool that helps identify potential problems in a React application.

Example:

```jsx
<StrictMode>
```

No. Its development checks do not behave the same way in production builds.

# 36. React 18 / Concurrent Rendering Concepts

### 38. What is concurrent rendering?

Concurrent rendering allows React to work on rendering tasks in an interruptible way, so urgent work can be prioritized over less urgent work.

The important idea is:

```text
Urgent update
     ↓
Higher priority

Non-urgent update
     ↓
Can be interrupted/deferred
```

```jsx
const [isPending, startTransition] = useTransition();
```

This can help keep urgent interactions responsive while React works on less urgent rendering.

```text
    ↓
Non-urgent
```

```jsx
const deferredQuery = useDeferredValue(query);
```

This can be useful when an expensive component should update less urgently than the input.

# 40. Large Lists

Don't render all 10,000 DOM nodes simultaneously if the UI doesn't require it.

Conceptually:

```text
10,000 records
       ↓
Only visible ~20-50 records
       ↓
Render those
```

Libraries such as `react-window` or other virtualization solutions can help.

# 41. Debouncing

### 43. What is debouncing?

Debouncing delays execution until the user stops triggering an event for a specified period.

Example:

```text
User types:

R
Re
Rea
Reac
React

Instead of:
5 API calls

Debounce:
1 API call
```

Common use case:

```text
Search box
   ↓
Wait 300ms
   ↓
API call
```

# 42. Throttling

### 44. What is throttling?

Throttling limits how frequently a function can execute.

Example:

```text
Scroll event
 ↓
Instead of executing 100 times
 ↓
Execute at most once per interval
```

### Follow-up: Debounce vs throttle?

| Debounce                   | Throttle                         |
| -------------------------- | -------------------------------- |
| Waits until activity stops | Executes at controlled intervals |
| Search input               | Scroll                           |
| Resize                     | Mouse movement                   |
| Form validation            | Continuous events                |

# 44. Race Conditions

### 46. What is an API race condition?

Suppose the user searches:

```text
React
```

then immediately:

```text
ReactJS
```

If the first request finishes after the second request, stale data could overwrite the latest result.

A senior developer should know how to handle this using mechanisms such as:

* `AbortController`
* Request IDs
* Query libraries
* Proper effect cleanup

# 53. Context Performance

### 55. What is a common performance problem with Context?

If the Context provider's value changes, consumers that use that context may need to re-render.

For example:

```jsx
<AuthContext.Provider value={{ user, login }}>
```

Creating a new object on every render can also change the context value's identity.

Depending on the case, you might use:

```jsx
const value = useMemo(
    () => ({ user, login }),
    [user, login]
);
```

But optimization should be driven by actual performance needs.

# 54. useMemo Misuse

### 56. Why can excessive useMemo be bad?

`useMemo` itself has overhead and adds complexity.

Bad approach:

```jsx

```

There's usually no meaningful benefit.

Prefer simple code unless the calculation is expensive or memoization solves a specific rendering problem.

# 55. Referential Equality

### 57. What is referential equality and why is it important in React?

Consider:

```jsx
const a = { name: "John" };
const b = { name: "John" };
```

Although their contents are the same:

```javascript
a === b
```

is:

```text
false
```

React optimizations such as `React.memo` and dependency comparisons can be affected by object/function identity.

This is why unnecessary creation of objects/functions can sometimes cause child components or effects to update.

# 56. Stale Closures

### 58. What is a stale closure?

A stale closure occurs when a function captures an older value from a previous render.

Example:

```jsx
useEffect(() => {
    const timer = setInterval(() => {
        console.log(count);
    }, 1000);

    return () => clearInterval(timer);
}, []);
```

The callback can continue seeing the value captured when the effect was created.

Solutions depend on the use case, such as:

```jsx
setCount(prev => prev + 1);
```

or correctly managing dependencies/refs.

# 73. Infinite useEffect Loop

### 75. Why can this cause an infinite loop?

```jsx
const [user, setUser] = useState({});

    setUser({
        name: "John"
```

Flow:

```text

 ↓
effect runs
 ↓
setUser()
 ↓
new object created
 ↓
user changes
 ↓
effect runs
 ↓
...
```

The dependency changes because a new object reference is created.

# React Internals

## 1. How does reconciliation work?

### Answer

**Reconciliation** is the process React uses to compare the previous rendered element tree with the new rendered element tree and determine what needs to change in the UI.

For example:

```jsx
function App() {
    const [count, setCount] = useState(0);

    return <h1>{count}</h1>;
}
```

Initially:

```text
<h1>0</h1>
```

After:

```javascript
setCount(1);
```

React produces a new element representation:

```text
<h1>1</h1>
```

React then reconciles the old and new trees and commits the necessary DOM update.

Conceptually:

```text
State / Props change
       ↓
React renders
       ↓
New element tree
       ↓
Reconciliation
       ↓
Determine changes
       ↓
Commit DOM updates
```

### Follow-up: Does React compare every DOM node?

Not in the simplistic sense of doing a full expensive DOM comparison every time.

React uses heuristics and element identity to efficiently reconcile trees. **Keys** are especially important for lists.

---

# 2. How does React decide what to update?

React considers things such as:

* Element type
* Props
* Children
* Keys
* Component state
* Context
* Updates scheduled by the application

For example:

```jsx
<div>
    <h1>Hello</h1>
</div>
```

becomes:

```jsx
<div>
    <h1>Hello React</h1>
</div>
```

React can preserve the existing `div` and `h1` DOM nodes and update the text content.

### Follow-up: What happens if the element type changes?

For example:

```jsx
<div>Hello</div>
```

becomes:

```jsx
<span>Hello</span>
```

Because the element type changed from `div` to `span`, React generally treats this as a different element and replaces that subtree rather than simply updating the existing DOM element's tag.

---

# 3. What is React Fiber?

### Answer

**Fiber** is the internal architecture React uses to represent and process rendering work.

It allows React to break rendering work into smaller units and assign priorities to updates.

Conceptually:

```text
React Update
     ↓
Fiber tree
     ↓
Rendering work
     ↓
Prioritize / schedule work
     ↓
Commit changes
```

Fiber is an important foundation for modern React capabilities such as interruptible rendering and concurrent features.

### Follow-up: Why was Fiber introduced?

Older React rendering was more synchronous and difficult to interrupt.

Fiber allows React to better control rendering work, including:

* Prioritization
* Interrupting work
* Resuming work
* Scheduling
* More responsive rendering

---

# 4. What is concurrent rendering?

### Answer

Concurrent rendering means React can work on rendering updates in an interruptible manner.

It doesn't mean React creates multiple threads.

Instead, React can:

```text
Start rendering
      ↓
Pause if necessary
      ↓
Handle more urgent work
      ↓
Resume / discard / continue rendering
```

For example, imagine a search page with thousands of results.

Typing into the input is urgent:

```text
User typing
     ↓
High priority
```

Updating a huge result list can be treated as less urgent:

```text
Result rendering
     ↓
Lower priority
```

This is where APIs such as `useTransition` can help.

### Follow-up: Is concurrent rendering the same as multithreading?

**No.**

JavaScript in the browser normally runs on a single main thread for this work. Concurrent rendering is about React's ability to **schedule and interrupt rendering work**, not about executing React rendering simultaneously on multiple CPU threads.

---

# 5. What is automatic batching?

### Answer

Batching means React groups multiple state updates together so it can avoid unnecessary rendering work.

For example:

```jsx
function updateUser() {

    setName("John");
    setAge(30);
}
```

React can batch these updates so they result in fewer renders.

Modern React also supports automatic batching in more asynchronous situations than older React versions.

### Follow-up: Why is batching useful?

Without batching:

```text
setName()
 ↓
render

setAge()
 ↓
render
```

Potentially:

```text
2 updates → 2 renders
```

With batching:

```text
setName()
setAge()
   ↓
one rendering/commit opportunity
```

This can improve performance.

---

# 6. What causes a component to re-render?

A component can render again because of:

### 1. Its state changes

```jsx
setCount(count + 1);
```

### 2. Its parent renders

A parent rendering can cause its child to be evaluated again, although memoization and other optimizations can allow React to skip work.

### 3. Context changes

If a component consumes a context whose value changes, it can render again.

### 4. External store updates

Libraries and APIs using external stores can trigger subscribed components to update.

### Follow-up: Does a re-render always mean the DOM changes?

**No.**

This is an important interview point.

```text
Component renders
       ↓
React reconciliation
       ↓
Does DOM actually need to change?
       ↓
Maybe / Maybe not
```

A render is not the same thing as a DOM mutation.

---

# 7. How does React.memo work?

### Answer

`React.memo` allows React to skip rendering a function component when its props haven't changed according to the memo comparison.

Example:

```jsx
const User = React.memo(function User({ name }) {
    console.log("User rendered");

    return <h1>{name}</h1>;
});
```

If the parent renders again but `name` remains the same, React may skip rendering `User`.

### Follow-up: Does React.memo guarantee that the component won't render?

**No.**

It is a performance optimization, not a guarantee.

The component can still render because of:

* Its own state
* Context it consumes
* Changed props
* Other React update behavior

### Follow-up: What comparison does React.memo use?

By default, React uses a shallow comparison based on prop identity using `Object.is` semantics.

This is where referential equality becomes important.

---

# 8. How does referential equality affect rendering?

Consider:

```javascript
const user1 = {
    name: "John"
};

const user2 = {
    name: "John"
};
```

Even though the objects contain the same data:

```javascript
user1 === user2
```

returns:

```text
false
```

because they are different object references.

Now:

```jsx
const User = React.memo(({ user }) => {
    return <h1>{user.name}</h1>;
});
```

If you do:

```jsx
<User user={{ name: "John" }} />
```

a new object can be created on each parent render.

Therefore, the prop reference changes.

### Follow-up: How can you stabilize the object?

Potentially:

```jsx
const user = useMemo(() => ({
    name: "John"
}), []);
```

But don't add `useMemo` automatically. First determine whether the optimization is actually useful.

---

# 9. How do keys affect reconciliation?

Keys give list items a stable identity.

Example:

```jsx
users.map(user => (
    <User
        key={user.id}
        user={user}
    />
))
```

Suppose:

```text
Before:

A
B
C
```

After:

```text
X
A
B
C
```

With stable keys, React can recognize:

```text
X → new
A → existing
B → existing
C → existing
```

### Follow-up: Why shouldn't we normally use index as key?

Consider:

```jsx
key={index}
```

If items are inserted or removed from the beginning/middle of the list, indexes can change.

That can cause React to associate component state with the wrong item.

Prefer:

```jsx
key={user.id}
```

when you have a stable unique ID.

# Hooks

# 10. Why do Hooks have rules?

Hooks rely on a consistent call order between renders.

Correct:

```jsx
function App() {

    const [count, setCount] = useState(0);
    const [name, setName] = useState("");

}
```

Incorrect:

```jsx
if (isLoggedIn) {
    const [name, setName] = useState("");
}
```

On different renders, the number/order of Hook calls could change.

React would no longer be able to reliably associate Hook state with the correct Hook call.

### Rules

Hooks should be called:

* At the top level
* Not inside loops
* Not inside conditions
* Not inside nested functions
* From React function components or custom Hooks

---

# 11. What causes stale closures?

A closure captures variables from the render in which the function was created.

Example:

```jsx
function Counter() {

    const [count, setCount] = useState(0);

    useEffect(() => {

        const timer = setInterval(() => {
            console.log(count);
        }, 1000);

        return () => clearInterval(timer);

    }, []);

}
```

The callback captures the `count` value from the render where that effect was created.

Therefore, it can keep seeing an old value.

### Follow-up: How can we solve stale state when updating?

Use a functional state update when the new value depends on the previous value:

```jsx
setCount(prev => prev + 1);
```

Other solutions include:

* Correct dependencies
* `useRef` when you genuinely need a mutable latest value
* Restructuring the effect

---

# 12. How do dependency arrays work?

Example:

```jsx
useEffect(() => {
    fetchUser(userId);
}, [userId]);
```

The effect is synchronized with `userId`.

When `userId` changes:

```text
userId changes
     ↓
effect re-runs
```

React compares dependencies between renders using `Object.is` semantics.

### Three common forms

#### No dependency array

```jsx
useEffect(() => {
    // ...
});
```

Runs after every completed render.

#### Empty array

```jsx
useEffect(() => {
    // ...
}, []);
```

No changing dependencies are specified; in typical client-side usage, it runs after the initial mount.

#### Dependency array

```jsx
useEffect(() => {
    // ...
}, [userId]);
```

Runs after the initial mount and when `userId` changes.

### Follow-up: Why should we not simply remove dependencies to stop an effect from running?

Because the dependency array describes what the effect depends on.

Removing a dependency can create stale values or incorrect synchronization.

---

# 13. When should you use useRef?

Use `useRef` when you need a value that:

1. Persists across renders
2. Can change without triggering a render

### DOM example

```jsx
const inputRef = useRef(null);

<input ref={inputRef} />
```

Then:

```jsx
inputRef.current.focus();
```

### Mutable value example

```jsx
const timerRef = useRef(null);
```

### Follow-up: Does changing `ref.current` trigger a render?

**No.**

```jsx
ref.current = 10;
```

does not cause React to render again.

---

# 14. useMemo vs useCallback

### `useMemo`

Caches a **calculated value**.

```jsx
const total = useMemo(() => {
    return calculateTotal(items);
}, [items]);
```

### `useCallback`

Caches a **function reference**.

```jsx
const handleClick = useCallback(() => {
    saveUser(user);
}, [user]);
```

Think:

```text
useMemo
   ↓
memoize VALUE

useCallback
   ↓
memoize FUNCTION
```

### Follow-up: Why would useCallback matter with React.memo?

Suppose:

```jsx
const Child = React.memo(({ onClick }) => {
    // ...
});
```

If the parent creates a new function on every render:

```jsx
<Child onClick={() => save()} />
```

the function reference can change.

A properly scoped `useCallback` can provide a stable function reference when that actually benefits the memoized child.

---

# 15. useEffect vs useLayoutEffect

### `useEffect`

Runs after React commits the DOM update and generally after the browser has had an opportunity to paint.

Use it for synchronization with external systems such as:

* API requests
* Subscriptions
* Timers
* Event listeners

### `useLayoutEffect`

Runs synchronously after DOM mutations but before the browser paints.

Use it when you need to:

* Measure DOM
* Calculate layout
* Make synchronous DOM-related adjustments

Example:

```jsx
useLayoutEffect(() => {
    const height = elementRef.current.offsetHeight;
}, []);
```

### Follow-up: Which one should you prefer?

Usually:

```text
useEffect
```

Use `useLayoutEffect` only when you specifically need its timing.

---

# 16. useState vs useReducer

### useState

Good for simple state:

```jsx
const [name, setName] = useState("");
```

### useReducer

Good for complex state transitions:

```jsx
const [state, dispatch] = useReducer(reducer, initialState);
```

For example:

```text
Form state
 ├── name
 ├── email
 ├── password
 ├── loading
 └── error
```

Many actions may modify these values.

### Follow-up: Is useReducer better than useState?

No.

Neither is universally better.

Use:

```text
useState
→ simple state

useReducer
→ complex state transitions
```

---

# 17. When should you create a custom Hook?

Create a custom Hook when you have **reusable stateful behavior or React-specific logic**.

Example:

```jsx
function useDebounce(value, delay) {
    const [debouncedValue, setDebouncedValue] = useState(value);

    useEffect(() => {
        const timer = setTimeout(() => {
            setDebouncedValue(value);
        }, delay);

        return () => clearTimeout(timer);
    }, [value, delay]);

    return debouncedValue;
}
```

Usage:

```jsx
const debouncedSearch = useDebounce(search, 300);
```

### Important interview point

A custom Hook reuses **logic**, not UI.

```text
UI reuse
→ Component

Logic reuse
→ Custom Hook
```

# 18. How do you debug unnecessary renders?

Don't immediately add `useMemo` and `React.memo`.

First **measure**.

Use React DevTools Profiler and browser performance tools.

Check:

```text

        ↓
Why did it render?
        ↓
Parent update?
Props?
State?
Context?
External store?
        ↓
Is the rendering actually expensive?
```

Then optimize.

### Follow-up: What optimizations can you use?

Depending on the problem:

* Component restructuring
* Keep state local
* `React.memo`
* `useMemo`
* `useCallback`
* Context splitting
* Virtualization
* Code splitting

# 19. How do you optimize a large list?

Suppose you have:

```text
100,000 users
```

Don't render all 100,000 DOM elements if the UI only needs a small visible portion.

Use:

### Virtualization

```text
100,000 records
       ↓
Visible viewport
       ↓
Render only ~20-100 rows
```

You can use a virtualization library or implement an appropriate windowing strategy.

Also consider:

* Pagination
* Server-side filtering
* Server-side sorting
* Memoized row components where useful

# 20. How do you reduce bundle size?

Strategies include:

### 1. Code splitting

Load code when needed.

### 2. Lazy loading

```jsx
const Admin = lazy(() => import("./Admin"));
```

### 3. Remove unused dependencies

Don't import a huge library for one small function if a lighter alternative is appropriate.

### 4. Analyze the bundle

Use your build tool's bundle analysis capabilities.

### 5. Optimize assets

Images and fonts can also contribute significantly to page weight.

### Follow-up: What is tree shaking?

Tree shaking is the build process of eliminating unused code from the final bundle when the module/bundler setup supports it.

# 21. How do you implement code splitting?

Use dynamic imports.

```jsx
const Reports = lazy(
    () => import("./Reports")
);
```

Then:

```jsx
<Suspense fallback={<Loading />}>
    <Reports />
</Suspense>
```

Conceptually:

```text
Initial bundle
     ↓
Application loads
     ↓
User opens Reports
     ↓
Reports chunk downloaded
```

This reduces the initial JavaScript that must be loaded.

# 22. When should you use memoization?

Use memoization when it solves a demonstrated performance problem.

Potential use cases:

### Expensive calculation

```jsx
const result = useMemo(
    () => expensiveCalculation(data),
    [data]
);
```

### Stable callback for a memoized child

```jsx
const handleClick = useCallback(
    () => save(id),
    [id]
);
```

### Prevent unnecessary child rendering

```jsx
const Child = React.memo(...);
```

### Follow-up: Why shouldn't we memoize everything?

Because memoization:

* Adds complexity
* Has its own runtime/memory costs
* Can make code harder to understand
* May provide no measurable benefit

**Senior answer: Profile first.**

# 24. How would you optimize a slow search page?

A typical architecture:

```text
User types
   ↓
Local input state
   ↓
Debounce
   ↓
API request
   ↓
Loading
   ↓
Results
```

For example:

```jsx
const debouncedQuery = useDebounce(query, 300);
```

Then fetch based on:

```jsx
useEffect(() => {
    search(debouncedQuery);

```

* Request cancellation
* Race conditions
* Caching
* Pagination
* Server-side filtering
* Loading states
* Empty states
* Error handling

Without debounce:

```text

 ↓

```

With debounce:

```text
10 characters
 ↓

 ↓
1 API request
```

# 26. How do you decide between Context and Redux?

Don't think of this as simply:

```text
Context vs Redux
```

First ask:

> What kind of state am I managing?

### Context

Good for relatively stable cross-cutting values such as:

```text
Theme

Authentication context

```

### Redux / other state-management solution

Useful when application state is:

* Shared widely
* Complex
* Frequently updated
* Requires predictable state transitions
* Needs strong debugging/devtools

Context is primarily a **mechanism for passing values through the component tree**.

# 28. How do you design reusable components?

### 5. Avoid unnecessary coupling

```text
 ↓

 ↓

 ↓
```

# 30. How do you design authentication?

A senior-level answer should separate **authentication** from **authorization**.

### Authentication

> Who is the user?

Typical flow:

```text
Login
 ↓
Backend authentication
 ↓
Session/token
 ↓
Authenticated requests
 ↓
Authenticated UI
```

### Authorization

> What is the user allowed to do?

For example:

```text
Admin
 ↓
Can delete users

Employee
 ↓
Can view users
```

You also need to consider:

* Session/token expiration
* Refresh
* Logout
* Unauthorized API responses
* Secure credential storage
* CSRF where cookie-based authentication is used
* XSS
* CORS
* Backend authorization

### Follow-up: Should authentication be implemented only in React?

**No.**

React can control the UI, but the backend must enforce authorization.

For example, hiding:

```jsx
{isAdmin && <DeleteButton />}
```

is not security.

The API must still verify that the user is authorized to delete the resource.

# 32. How do you design role-based authorization?

Suppose your application has:

```text
ADMIN
MANAGER
EMPLOYEE
```

Don't only control what appears in React.

You can use React for UI-level authorization:

```jsx
{user.role === "ADMIN" && (
    <DeleteButton />
)}
```

But the backend must enforce the actual permission:

```text
DELETE /api/users/10
          ↓
Backend
          ↓
Check authentication
          ↓
Check permission
          ↓
Allow / Deny
```

### Better approach

Instead of scattering role checks everywhere:

```jsx
user.role === "ADMIN"
```

you can centralize permission logic:

```jsx
can(user, "DELETE_USER")
```

Then:

```jsx
{can(user, "DELETE_USER") && (
    <DeleteButton />
)}
```

### Follow-up: Can frontend authorization provide security?

**No.**

Frontend authorization improves UX.

**Backend authorization provides security.**

A user can bypass your React UI and call your API directly, so the server must always enforce permissions.
